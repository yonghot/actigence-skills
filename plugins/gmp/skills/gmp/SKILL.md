# GMP v2.7: General Meta-Prompt Protocol

프롬프트 또는 스킬의 생성·개선 요청이 감지되면, 아래 프로토콜을 적용하여 최고 수준의 프롬프트/스킬을 산출하라.

## 사용 판정

이 스킬이 트리거되면 먼저 사용자의 요청을 판정하라:

- **프롬프트 신규 생성**: 사용자가 작업 설명을 제공하고 프롬프트를 만들어달라고 요청 → 아래 프로토콜로 프롬프트를 새로 설계
- **프롬프트 개선**: 사용자가 이미 작성된 프롬프트를 제공하고 개선을 요청 → 아래 프로토콜에 따라 기존 프롬프트를 최고 수준으로 개선. 단, 기존 프롬프트에 이미 적용된 기법(이중 앵커링, XML 구조, 자기검증 등)은 중복 적용하지 말고 기존 구조 내에서 내용을 개선하라.
- **스킬 신규 생성**: 사용자가 스킬(SKILL.md)을 만들어달라고 요청 → 아래 프로토콜로 스킬의 핵심 지시문(SKILL.md 본문)을 설계. 스킬의 frontmatter(name, description)와 파일 구조는 skill-creator 스킬이 있으면 그 규격을, 없으면 아래 '스킬 산출 체크리스트'를 따르되, 본문의 지시 품질은 GMP 프로토콜로 보장
- **스킬 개선**: 사용자가 기존 스킬을 제공하고 개선을 요청 → 아래 프로토콜에 따라 스킬의 지시문 품질을 최고 수준으로 개선. 기존 스킬에 이미 적용된 구조적 기법은 중복 적용하지 말고 내용 품질만 개선하라.
- **판정 불가**: 프롬프트/스킬 생성·개선 의도가 불확실하면 사용자에게 확인

### 스킬 산출 체크리스트 (스킬 생성·개선 시에만)

산출 전에 아래를 모두 확인한다.

- 폴더명 = frontmatter `name`. frontmatter 는 `name`·`description` 만 둔다.
- `description` 은 1024자 이하이며 무엇을 하는지, 언제 쓰는지, 언제 쓰지 않는지(인접 스킬 이름 포함)를 담는다. 글자 수를 실제로 세어 확인한 뒤 전달한다.
- 본문은 약 500줄 이하로 두고, 긴 자료는 `references/` 로 분리해 본문에서 상대 경로로 가리킨다.
- 특정 사용자 홈 폴더를 가리키는 절대 경로를 넣지 않는다(상대 경로를 쓴다).
- 스크립트를 포함하면 필요한 패키지와 설치 명령을 SKILL.md 에 적는다.

## GMP 프로토콜 전문

아래는 사용자의 입력에 적용할 프로토콜이다. "위 내용"은 사용자가 제공한 작업 설명, 기존 프롬프트, 또는 기존 스킬을 가리킨다.

<CRITICAL_ANCHOR>
이 프롬프트의 최우선 목표: 위 내용이 작업 설명이면 그에 최적화된 프롬프트/스킬을 새로 설계하고, 이미 프롬프트/스킬이면 아래 프로토콜에 따라 최고 수준으로 개선하라. 파일 접근이 가능한 에이전트 환경(예: Claude Code)에서 서브에이전트를 적극 활용하여 최고 품질의 결과물을 산출하는 구조로 만들라.
생성되는 프롬프트/스킬은 반드시 XML 태그 기반 계층 구조를 사용하라.
핵심 제약조건은 생성되는 프롬프트/스킬의 최상단과 최하단에 이중 배치하라.
</CRITICAL_ANCHOR>

---

<PHASE_1_DECOMPOSE>
위 내용을 아래 8개 축으로 분해하라(개선 모드에서는 9번까지). 이 분석은 내부적으로 수행하되, 출력하지 마라.

1. 핵심 동사: 생성 / 분석 / 변환 / 검증 / 설계 / 비교 중 어느 유형인가
2. 입력물과 출력물: 형태, 분량, 파일 포맷
3. 필수 제약조건: 위반 시 작업이 실패하는 것들
4. 암묵적 기대사항: 명시되지 않았으나 당연히 포함되어야 하는 것
5. 품질 기준: 무엇이 "좋은" 결과이고, 무엇이 "나쁜" 결과인가
6. 예측 가능한 실패 패턴: 이 유형의 작업에서 흔히 발생하는 오류
7. 복잡도 판정 — 작업 난이도에 따라 프롬프트의 지시 깊이를 조절하라:
   - 단순 (단일 단계, 명확한 출력) → 추론 유도 불필요. 간결한 프롬프트 생성.
   - 중간 (다단계 처리, 조건 분기) → Plan-and-Solve 적용
   - 고도 (전문 지식 추론, 다중 도메인) → Step-Back Abstraction 적용
   - 정확성 핵심 (팩트체크, 데이터 검증) → Chain-of-Verification 적용
   단순한 작업에 과도한 구조를 부여하면 오히려 성능이 저하된다. 작업 난이도가 프롬프트 복잡도를 결정하게 하라.
8. 타겟 모델 추정 — 생성되는 프롬프트가 실행될 모델의 reasoning 능력에 따라 추론 기법 적용을 조절하라:
   - Reasoning model (Claude 5 계열 등 내장 추론 모델, OpenAI·Google의 최신 추론 모델) → 명시적 CoT/Plan-and-Solve 지시는 중복이거나 역효과일 수 있다는 연구 보고가 있다. PHASE_3의 Thinking Steering으로 대체하라.
   - Non-reasoning model 또는 reasoning 비활성 상태 → 7번 복잡도 판정 결과대로 CoT/Plan-and-Solve/Step-Back 적용.
   - 타겟 모델 불명 → 안전 기본값: 7번 권장 기법 적용하되 Thinking Steering도 병기.

개선 모드인 경우 추가 분석:
9. 기존 기법 탐지: 위 내용에 이미 적용된 프롬프트 엔지니어링 기법을 식별하라.
   탐지 대상: 이중 앵커링, XML 구조, 우선순위 라벨링, 자기검증, 서브에이전트 설계, 중간 리마인더, Few-shot 예시 등.
   이미 적용된 기법 → 중복 추가하지 말고 기존 구조 내에서 내용만 개선.
   미적용이지만 유익한 기법 → 새로 추가.
   적용되었으나 품질이 낮은 기법 → 기존 구조를 유지하면서 내용을 교체·보강.
</PHASE_1_DECOMPOSE>

[구조 기법 — 거의 항상 적용]
• XML 태그 기반 섹션 구조
• 이중 앵커링 (CRITICAL_CONSTRAINTS + FINAL_REMINDER)
• 우선순위 라벨링 ([MUST] / [SHOULD] / [NICE])
• 긍정형 지시 원칙: 모든 제약을 "~하라" 형태로 서술. "~하지 마라"는 안전 경계에만 최소 사용

[추론 기법 — 복잡도에 따라 선택]
• Plan-and-Solve: 다단계 작업 시 "먼저 문제를 이해하고, 관련 변수를 추출하고, 완전한 계획을 수립한 뒤 단계별로 실행하라"
• Step-Back Abstraction: 전문 지식 추론 시 "먼저 이 문제의 상위 원칙/개념을 도출한 뒤, 그로부터 구체적 답을 도출하라"
• Chain of Draft: 토큰 효율이 중요할 때 "각 추론 단계를 5단어 이내의 최소 초안으로 유지하라"
• Chain-of-Verification: 정확성이 핵심일 때 위 SELF_VERIFICATION 섹션 활성화
• Thinking Steering: 타겟이 내장 추론 모델인 경우 명시적 CoT 지시 대신 사고량만 조절하라. 깊은 사고가 필요하면 "답하기 전에 충분히 깊게 생각하라, 보기보다 어려운 문제다"는 취지의 한 문장을, 빠른 응답이 우선이면 "깊은 사고보다 빠른 응답을 우선하라"는 취지의 한 문장만 둔다. 단계별 사고 틀(scaffold)은 두지 않는다. 내장 추론 모델에 CoT 지시는 중복이거나 응답 시간만 늘릴 수 있다는 보고가 있다.

[품질 기법 — 상황에 따라 선택]
• Few-shot 예시 (1-2개): 출력 형식이 비표준이거나 모호할 때만
• 역할 부여: 구체적 도메인 전문성이 필요할 때만. 수식어 없이 맥락만 부여
• 자기검증 체크리스트: 정확성이 핵심이거나 다수의 제약조건이 있을 때
• 조건부 분기: 입력 유형에 따라 처리 경로가 달라질 때

[에이전트 기법 — 에이전트 환경(파일 접근 가능)에서 적극 활용]
• 서브에이전트 분할: 작업이 2개 이상의 독립적 하위 작업으로 분해 가능할 때
• 오케스트레이터 패턴: 하나의 주 에이전트가 서브에이전트 결과를 통합·검증
• PROGRESS.md 핸드오프: 장기 작업에서 각 단계 완료 상태와 결과를 기록
• 병렬 실행 지시: 독립적인 서브태스크를 동시 처리하여 총 작업시간 단축
• 사전 검증 단계: "코드를 작성하기 전에 먼저 ~를 확인하라" 류의 guard clause

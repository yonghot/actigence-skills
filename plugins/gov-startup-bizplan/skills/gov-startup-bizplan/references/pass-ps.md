<table_cell_protocol>
## 표 기입 절차 (RULE-5 구현)

표는 "라벨 셀"과 "값 셀"로 구분된다. 내용은 반드시 "값 셀"에만 기입한다.

라벨 셀 (읽기 전용, 절대 수정하지 않는다):
  "명 칭", "아이템 개요", "문제 인식", "실현 가능성", "성장전략", "팀 구성" 등

값 셀 (여기에만 내용을 기입한다):
  ※ 파란색 안내문구가 있는 셀

기입 절차:
  1. field_map으로 라벨 텍스트를 검색한다 (예: "아이템 개요")
  2. 매핑된 값 셀 좌표를 확인한다 (예: row=2, col=1)
  3. 해당 셀의 기존 내용을 확인한다 → ※ 안내문구가 있으면 올바른 셀이다
  4. ★ 셀 안의 파란색 안내문구를 제거한다:
     - 셀 안에 텍스트박스(mc:AlternateContent / w:txbxContent)가 있는 경우:
       텍스트박스 안의 텍스트만 지우면 빈 텍스트박스 껍데기가 셀에 남아서 레이아웃이 깨진다.
       텍스트박스 XML 요소(mc:AlternateContent) 자체를 통째로 제거하여 셀을 완전히 비운다.
     - 셀 안에 텍스트박스 없이 일반 파란색 run만 있는 경우:
       해당 파란색 run을 제거한다.
  5. 셀이 비워진 것을 확인한 후 새 내용을 기입한다

★ 값 셀이 라벨 셀과 같은 행의 오른쪽에 있거나, 바로 아래 행에 병합되어 있을 수 있다
★ 확신이 없으면 해당 셀의 기존 텍스트에 ※가 포함되어 있는지 확인한다
</table_cell_protocol>

<chapter_1_일반현황>
## 1. 일반현황 표

★ 일반현황은 양식에 원래 존재하는 표 형태 그대로 유지한다 (RULE-4).
  표를 삭제하고 텍스트 한 줄로 변환하면 안 된다.
  표의 각 셀에 field_map과 table.cell을 사용하여 기입한다.

기입할 항목과 데이터 소스:
  - 창업아이템명: PRD에서 추출
  - 산출물(협약기간 내 목표): PRD에서 추출
  - 직업: "2." 폴더의 team_data에서 추출 (RULE-7)
  - 기업명: "2." 폴더의 team_data에서 추출 (RULE-7)
  - 팀 구성 현황 표: "2." 폴더의 team_data 팀원 전원을 기입한다. 빈 행을 방치하지 않는다

★ 대표자명·기업명 기입 시 주의:
  반드시 "2." 폴더의 신분증/이력서/첨부 서류에서 확인한 이름과 기업명을 사용한다
  참고 사업계획서에 나오는 다른 대표자명·기업명을 혼동하여 기입하면 안 된다
  확신이 없으면 "2." 폴더 파일을 다시 열어 실제 이름과 기업명을 확인한 후 기입한다
</chapter_1_일반현황>

<chapter_2_개요>
## 2. 개요 표

각 셀에 • 불렛으로 1.5페이지 이상 분량을 채운다.

셀 위치 주의사항:
  - "명 칭" 라벨 셀이 아니라, 그 옆의 값 셀에 서비스명을 기입한다
  - "아이템 개요" 라벨 셀이 아니라, 그 옆/아래의 값 셀에 내용을 기입한다
  - "문제 인식" 라벨 셀이 아니라, 값 셀에 기입한다. 이하 동일
  - 개요 표의 "팀 구성" 값 셀: team_data("2." 폴더)만 사용한다 (RULE-7)
</chapter_2_개요>

<chapter_3_problem>
## 3. Problem 챕터

### ㅇ 시장 현황 — • 5개 이상 (각 2~4줄)
  국내외 시장 규모, CAGR, 성장 드라이버를 구체적 수치와 함께 서술한다
  각 •에 출처 "(기관명, 연도)"를 필수로 병기한다 (RULE-2)

### ㅇ 핵심 문제 — (1)(2)(3), 문제당 • 3개 이상
  문제를 3개 이상으로 구분하여 체계적으로 제시한다
  각 문제의 현황·영향·규모를 구체적 수치와 함께 서술한다

### ㅇ 기존 솔루션 한계 + Unmet Need — • 5개 이상
  기존 경쟁사/대안의 구체적 한계점을 서술한다
  아직 해결되지 않은 시장의 미충족 니즈를 명시한다

★ "대표의 경험에서 발견한 문제" 류 서술 시:
  team_data.ceo의 실제 경력만 사용한다 (RULE-7)
</chapter_3_problem>

<chapter_4_solution>
## 4. Solution 챕터

### ㅇ 서비스 구조·기술 — • 5개 이상
  팀의 기술력, 대표 경력, CTO 역량 류 서술 시 → team_data만 사용한다 (RULE-7)

  기술 스택 서술 원칙:
    프레임워크·라이브러리 이름을 나열하는 대신, AI/독자 알고리즘 등 차별화 기술만
    "이 기술로 무엇이 가능한가" 관점으로 서술한다

### ㅇ 차별점 — (1)(2)(3), • 5개 이상
  경쟁사 대비 명확한 차별화 포인트를 제시한다
  각 차별점에 근거·수치·비교를 포함한다

### ㅇ TAM-SAM-SOM — 수치+근거+출처 필수
  TAM: Top-down 시장 규모
  SAM: 타겟 세그먼트
  SOM: Bottom-up 보수적 달성 가능 규모 (RULE-9)

### ㅇ 개발 계획 + 사업비 (표 + 산출근거)

사업비 집행계획은 1단계/2단계 각각 표로 작성한다 (RULE-8).
표의 컬럼 구조: | 비 목 | 산출 근거 | 정부지원사업비(원) |

★ "비목" 컬럼에 "인건비"와 "외주용역비"를 각각 별도 행으로 기입한다.
  하나의 비목 행에 인건비와 외주를 섞어 넣지 않는다.

<budget_format>
■ 인건비 행 — 산출 근거 작성법:
  고용할 인력의 직무명 + 인원수 + 월 단가 + 기간을 구체적으로 명시한다.
  인력이 여러 명이면 ■ 불렛으로 각각 분리한다.

  올바른 예시:
    비목: 인건비
    산출 근거:
      ■ 풀스택 개발자 1인(월 350만원 × 4개월)
      ■ UI/UX 디자이너 1인(월 300만원 × 3개월)
    금액: 각 인력별 소계 기입

  잘못된 예시:
    비목: 인건비
    산출 근거: 개발 인력 채용
    → 직무명·인원·단가·기간이 없으면 심사위원이 산출 근거를 파악할 수 없다

■ 외주용역비 행 — 산출 근거 작성법:
  외주 항목명 + 구체적 용도/범위 + 금액을 명시한다.
  외주가 여러 건이면 ■ 불렛으로 각각 분리한다.

  올바른 예시:
    비목: 외주용역비 (또는 양식에 따라 해당 비목명)
    산출 근거:
      ■ AI 수요 예측 모델 설계 외주(데이터 수집·전처리·모델 프로토타입)
      ■ 초기 메타(Instagram·Facebook) 마케팅 대행 외주
    금액: 각 외주 항목별 소계 기입

  잘못된 예시:
    비목: 외주용역비
    산출 근거: 외주 개발
    → 무엇을 외주하는지, 범위가 어디까지인지 불명확하면 사업비 적정성을 인정받기 어렵다
</budget_format>

<budget_summary>
■ 사업비 총괄 문구 (표 하단에 기입):
  "사업비 총괄: 1단계 N만원(인건비 A만+외주 B만) + 2단계 M만원(인건비 C만+외주 D만) = 합계 X만원(=최대 지원금). 인건비+외주용역비 2개 비목으로만 구성하여 집행 효율성 극대화"

  verify_budget_total로 1단계+2단계 합계 = 공고문 최대 지원금을 반드시 검증한다
</budget_summary>
</chapter_4_solution>
